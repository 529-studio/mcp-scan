mcp-scan is the first 5-minute security check for MCP servers. It finds unpinned packages, leaked secrets, shell wrappers, broad filesystem roots, wildcard binds, and write access granted by default. In live mode it also reads tools/list and flags dangerous descriptions, schemas, and annotations. Add --dynamic to probe read-only tools inside a sandbox — then it gives you the fix.

The problem

MCP gave agents real permissions. Your config didn’t get safer.

An MCP server can read files, query databases, call APIs, and run code. Most teams review the model. Almost nobody reviews the config that gives it the keys.

01

Tool poisoning

A tool description contains hidden instructions. The model reads it as policy, then does something you never approved.

02

Over-permission

A server can read the whole home directory, bind to 0.0.0.0, or write to production — because that was the default.

03

Secret leakage

API keys live in mcp.json, dotfiles, screenshots, and logs. One commit is all it takes.

How it works

Three steps. No agent required.

Deterministic checks first. Every finding has evidence, impact, and a fix.

STEP 01

Point at your config

Pass a directory or a file. mcp-scan finds mcp.json, claude_desktop_config.json, .cursor/mcp.json, and friends.

STEP 02

Run 20 static rules + dynamic probes

Transport, supply chain, secrets, permissions, network exposure, debug flags, write access — plus tool descriptions, schemas, hidden content, and annotations. Add --dynamic to call read-only tools inside a sandbox with disposable canaries.

STEP 03

Fix, then prove it

Each finding ships with a concrete fix. Re-run in CI, keep the evidence, answer the security questionnaire.

FAQ

The honest answers.

Is this a pentest?

No. It is a deterministic first pass over your MCP configuration, your tool manifest, and — when you opt in — a sandboxed behavioral probe. It catches common, high-signal mistakes. It does not replace a human review, fuzzing, or a pentest.

Does it connect to a live server?

Only when you ask. --live and --stdio perform the MCP initialize handshake and read tools/list. Add --dynamic to call read-only tools with canaries inside a sandbox. It never exploits a finding.

Does it exploit anything?

No. It never exploits a finding. Static and live modes do not call tools. Dynamic mode calls a small set of read-only tools with disposable canaries inside a sandbox, and only when you opt in.

Does it upload my config?

No. The CLI runs locally. The hosted dashboard is optional and will require explicit opt-in. Secrets are masked in reports.

What about false positives?

Every finding includes evidence so you can judge it. Rules are deliberately narrow. If a rule is noisy, open an issue with the config and we will fix or remove it.

Why Apache-2.0 and not AGPL?

Adoption and enterprise trust matter more than stopping every hosted clone. The moat is the hosted evidence layer, rule upkeep, and support — not the scanner source. Apache-2.0 also includes a patent grant.

Can I add a rule?

Yes. Add a check(server) function in src/rules.js or a check(tool) function in src/tool-rules.js, plus a fixture and a docs entry. See CONTRIBUTING.md.
